# Agent 单轮耗时

每个 Agent 单轮都会记录时间去向。没有这个分布，优化工具通道或模型循环都只能靠猜；而这个分布此前并不存在——trace 里有事件，但没有时间戳。

## 记录内容

- 业务 CLI 在任何 import 之前取一次启动时刻，并在自己的第一个请求里上报（`timing.startedAt`、`timing.firstCall`）。这是唯一能看见解释器启动与 import 的方式：宿主机只能看到在这些之后才到达的请求。同一进程后续的请求不再报启动，因此循环等待的命令只被计入一次启动，而不是每轮询一次就算一次。
- 传输层把它折算成工具事件上已有的 `spawn`（启动）与 `work`（命令本身）。工具调用不经过该传输的运行时两者都没有，此时账本只保留该次调用的墙钟时长。
- API 层按调用标识把工具事件折叠成一条，在本轮结束时写一次 `agent-runs/timing/<turn>.json`。

账本保存逐次调用的数字，外加每轮一份汇总。跨轮的占比留给离线分析，因此测量损坏最多丢一个文件，绝不会让一轮失败。

原始数字刻意不写进对话历史：数百个工具事件的单轮已经占满 CLI 回读的 64 KB，每个事件再加两个时间戳只会更糟。

## 读取方式

```sh
python3 scripts/bench_turn_timing.py --project <项目目录> [--json]
```

报告给出：整轮墙钟、调用总时长及其占比、启动时长及其占整轮与占调用的比例、未计入部分（模型思考与编排），以及单次调用的 P50 与 P90。

调用总时长是各调用墙钟区间的并集，每个区间都补上它实际付出的启动时间。调用会嵌套——运行 CLI 的 Bash 调用包含 CLI 调用——所以把时长直接相加会把内层的时间算两遍，得出比整轮还多的工具时间。`callSecondsSum` 与 `overlapSeconds` 显示这部分重复计算。

## 判据

占比以整轮墙钟为分母，而不是调用次数：批量已经压低了次数，而"便宜但重复很多次"与"昂贵但重复很少次"是两个不同的问题。

| 启动占整轮比例 | 决定 |
| --- | --- |
| > 40% | 用原生通道替换 CLI 传输。 |
| 20–40% | 原生通道与 CLI 并行。 |
| < 20% | 保留传输通道，转而减少调用与探测。 |

当超过一半时间落在工具调用之外时，减少轮次与探测的收益先于任何传输层改动。根本不报告启动耗时的运行时是把问题留作未决，而不是已回答：未知不等于零。

选档要求每次调用都有启动计时。没有经过传输的调用（例如 `--help` 探测）同样启动了进程，但它的启动没人看见，因此当 `startupCoverage` 小于 1 时，报告把结论写成未决，而不是给出某一档。

这些判据只作参考，不进入 CI。计时断言会继承网络、机器负载与服务商延迟的抖动；证据写进报告，不写进门槛。
